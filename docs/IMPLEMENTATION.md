# SOL AI — Resource Adapters & Foundational Architecture

## 1. Current Architecture

SOL AI utilizes a modular, resource-decoupled evidence architecture. Higher-level query engines and contextual processors consume normalized `Evidence` objects generated by resource adapters implementing a shared `ResourceAdapter` interface.

```text
                                         +-------------------+
                                         | SOL AI System     |
                                         +---------+---------+
                                                   |
                                                   v
                                       +-----------------------+
                                       | ResourceAdapter (ABC) |
                                       +-----------+-----------+
                                                   |
        +------------------------------------------+------------------------------------------+
        |                                          |                                          |
        v                                          v                                          v
+---------------------------+          +---------------------------+              +---------------------------+
| ThamizhiMorphAdapter      |          | ThaniThamizhAkarathiAdapter|             | TamilWordNetAdapter       |
+-------------+-------------+          +-------------+-------------+              +-------------+-------------+
              |                                      |                                          |
              v (WSL / Subprocess)                   v (Pre-processed JSON)                     v (SQLite Index DB)
+---------------------------+          +---------------------------+              +---------------------------+
| Foma Transducers (flookup)|          | data/processed/akarathi...|              | data/processed/wordnet... |
+---------------------------+          +---------------------------+              +---------------------------+
```

## 2. Evidence Model

Defined in `backend/schemas/evidence.py`. The `Evidence` dataclass serves as the canonical representation of linguistic, morphological, lexical, and literary evidence across all resource adapters:

- **surface**: Input surface word string.
- **lemma**: Extracted root or headword.
- **source**: Name of the resource adapter (e.g., `"ThamizhiMorph"`, `"Thani Thamizh Akarathi"`, `"Tamil WordNet"`).
- **evidence_type**: Type of evidence provided (e.g., `"morphology"`, `"lexical"`, `"frequency"`).
- **pos**: Part of speech category if identified (e.g., `"Verb"`, `"Noun"`).
- **morphology**: Feature string for morphological adapters.
- **meaning**: Dictionary definition or Tamil equivalent text for lexical adapters.
- **source_id**: Unique entry ID with file provenance.
- **metadata**: Key-value dictionary containing raw outputs, format descriptions, relation codes, and status.

## 3. ResourceAdapter Interface

Defined in `backend/resources/base.py`. Every resource adapter inherits from `ResourceAdapter` and implements the abstract method:

```python
class ResourceAdapter(ABC):
    @abstractmethod
    def lookup(self, query: str) -> List[Evidence]:
        pass
```

## 6. Tamil WordNet Integration

Implemented in `backend/resources/wordnet.py`.

### 6.1 Source Archive & Parsed Tables
- **Source**: `data/raw/tamil_wordnet/TamilWordnet.tgz` (`tvudump.sql`)
- **Parsed Tables**:
  - `twn`: **50,497** rows (nodes, labels, POS, relation & feature codes)
  - `sense`: **41,013** rows (senses, hypernyms, hypercounts)
  - `morphtable`: **434,849** rows (inflated words → root words)
  - `frequency`: **6,914** rows (corpus word frequency counts)

### 6.2 Encoding & Transliteration Strategy
- Source text is encoded in a Romanized Tamil phonetic scheme (e.g. `corkkam`, `iyaRkaikkappaaRpaTTavai`).
- **Deterministic Conversion**: Converts Romanized strings into modern Unicode Tamil (e.g., `சொர்க்கம்`, `இயற்கைக்கப்பாற்பட்டவை`).
- **Raw Data Preservation**: Original Romanized strings (`raw_label`, `raw_word`, `raw_root`) are preserved verbatim in `metadata` alongside Unicode labels.

### 6.3 SQLite Index Structure
- **Script**: `scripts/build_wordnet_index.py`
- **Output Database**: `data/processed/wordnet_index.db`
- Includes indexes on `unicode_label`, `raw_label`, `inflated_unicode`, and `word_unicode`.

### 6.4 Adapter Behavior & Raw Relations
- **Lexical Lookup**: Matches query in `twn_index` and `sense_index`.
- **Morphology Lookup**: Queries `morphtable_index` and returns root word as supporting evidence.
- **Frequency Lookup**: Attaches corpus frequency count in `metadata["corpus_frequency"]`.
- **Field Completeness**: Source dump fields `gloss`, `example`, and `english` are 100% NULL and preserved as `None` without fabricating fake definitions.
- **Raw Relation Codes**: Preserves raw numeric `relation_code` (e.g., `'3'`, `'4'`, `'1'`) and `feature_code` in metadata.

### 6.5 Commands & CLI Usage
```bash
python -m backend.resources.wordnet மரம்
python scripts/run_wordnet_benchmark.py
```

## 11. Unified Retrieval & Evidence Aggregation Layer

Implemented in `backend/query/normalizer.py`, `backend/retrieval/engine.py`, `backend/retrieval/aggregator.py`, and `backend/schemas/result.py`.

### 11.1 System Architecture
The unified retrieval layer coordinates deterministic evidence lookup across all four active resource adapters (`ThamizhiMorph`, `Thani Thamizh Akarathi`, `Tamil WordNet`, and `Sentamizh`):

```text
                               +-----------------------+
                               |      User Query       |
                               +-----------+-----------+
                                           |
                                           v
                               +-----------------------+
                               |    Query Normalizer   |
                               +-----------+-----------+
                                           |
                                           v
                               +-----------------------+
                               |   Retrieval Engine    |
                               | (Multi-Stage Query)   |
                               +-----------+-----------+
                                           |
                                           v
                               +-----------------------+
                               |  Evidence Aggregator  |
                               |  & Priority Ranker    |
                               +-----------+-----------+
                                           |
                                           v
                               +-----------------------+
                               |    Unified Result     |
                               +-----------------------+
```

### 11.2 Key Components
- **Query Normalizer** (`QueryNormalizer`): Applies Unicode NFC composition normalization and whitespace trimming without inventing hardcoded linguistic rules.
- **Retrieval Engine** (`RetrievalEngine`):
  - Executes **Pass 1 (Surface Lookup)** across all 4 adapters with resource-level error handling (adapter errors are logged in `UnifiedResult.errors` without crashing execution).
  - Extracts candidate lemmas discovered in Pass 1 morphological and dictionary root mappings.
  - Executes **Pass 2 (Lemma Lookup)** for discovered candidate lemmas against lexical and literary adapters (`Akarathi`, `WordNet`, `Sentamizh`).
- **Evidence Aggregator & Priority Ranker** (`EvidenceAggregator`):
  - Groups evidence by candidate lemma and source.
  - Computes `cross_resource_support` (identifies which candidate lemmas are supported by multiple independent resources).
  - Preserves conflicting and guesser FST analyses without silent deletion.
  - Applies transparent deterministic ranking (Core analyses > Guesser analyses; Surface exact matches > Lemma secondary matches; Direct evidence > Frequency-only).
- **Unified Result Schema** (`UnifiedResult`): Returns structured dataclass holding raw query, normalized query, candidate lemmas, preserved `Evidence` objects, resource summaries, cross-resource support mapping, and error logs.

## 13. Contextual Interpretation Layer

### 13.1 Architecture Overview
The **Contextual Interpretation Layer** (`backend/interpretation/`) sits directly above the verified deterministic retrieval layer. It converts `UnifiedResult` into a grounded, structured `SOLResponse` using an abstract LLM interpreter:

```
User Query
    ↓
Query Normalizer
    ↓
Unified Retrieval Engine
    ↓
Context Selector (SentamizhContextSelector)
    ↓
Evidence Pack Builder (build_evidence_pack)
    ↓
LLM Interpreter (BaseLLMInterpreter)
    ↓
Structured SOLResponse (Pydantic / JSON)
```

### 13.2 Core Components
1. **Pydantic Schemas (`backend/interpretation/schemas.py`)**:
   - `SOLResponse`: Grounded response containing query, lemma, meaning, morphology, contextual interpretation, literary context items, related words, sources, uncertainties, and evidence summary.
   - `LiteraryContextItem`: Preserves complete classical verse, work, period, verse number, author, and modern Tamil gloss.
   - `EvidencePack`: Un-flattened container preserving original `Evidence` objects categorized by type.
2. **Context Selector (`backend/interpretation/context_selector.py`)**:
   - Scores Sentamizh literary occurrences using multi-signal quality scoring (surface/lemma match, verse completeness, metadata richness).
   - Enforces a **work diversity constraint** so selected representative occurrences (3–5 max) span multiple distinct Sangam/Classical works rather than duplicate verses from a single text.
3. **Evidence Pack Builder (`backend/interpretation/evidence_pack.py`)**:
   - Categorizes raw evidence into morphology, lexical, selected literary, and related evidence categories.
   - Tracks source provenance and detects candidate lemma conflicts without altering original `Evidence` objects.
4. **Prompts & System Instructions (`backend/interpretation/prompts.py`)**:
   - Strict system prompt commanding zero fabrication, requiring all facts to be grounded in supplied evidence sections, and mandating valid structured JSON output.
5. **Provider Interface (`backend/interpretation/interpreter.py`)**:
   - `BaseLLMInterpreter`: Abstract interface.
   - `MockLLMInterpreter`: Grounded, deterministic offline interpreter for tests and keyless operation.
   - `GeminiLLMInterpreter`: REST API integration supporting Google Gemini models (`gemini-2.5-flash`).
   - `get_interpreter()`: Factory function reading `SOL_LLM_PROVIDER`.
6. **CLI Demo (`scripts/interpret_query.py`)**:
   - Direct execution script supporting `--debug` to output the un-flattened `EvidencePack` before the interpreted response.

```
    ↓

    ↓

```

### 14.2 REST API Endpoints (`backend/api/server.py`)
- **`GET /api/health`**:
  - Response: `{"status": "ok"}`
- **`POST /api/query`**:
  - Request: `{"query": "மரங்களில்", "provider": "optional"}`
  - Response: Grounded JSON response matching `SOLResponse` schema.
  - Error Handling: Returns 400 Bad Request for missing queries or unconfigured keys, and 500 for runtime exceptions without leaking stack traces or credentials.

### 14.3 Gemini Production Integration
- `SOL_LLM_PROVIDER=gemini`: Activates live Gemini LLM interpretation.
- `GEMINI_API_KEY`: Requires valid key; raises explicit `ValueError` if key is missing when Gemini provider is requested.
- `SOL_LLM_PROVIDER=mock`: Default offline development mode requiring zero API keys.
